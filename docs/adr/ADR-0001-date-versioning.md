# ADR-0001 版本号用日期式 `YYYY.MM.DD.N`，不用语义化版本

- 状态：已采纳
- 日期：2026-10-17（首次立规）/ 2026-10-23（成文）
- 相关版本：2026.10.17.1 起全部

## 背景

这些插件原本跟上游用 `0.9.x` / `0.12.x` 这类语义化版本，且各树独立计数
（workbuddy 到 0.9.71、qoder 到 0.8.72、trae 到 0.12.89……）。问题有三个：

1. **不知道哪个更新**。`0.9.71` 和 `0.12.89` 谁新？跨树比较要靠记忆。
2. **代次后缀满天飞**：`-v8.0` / `-ngN` / `-rpN` / `-xzyN`。同一棵树一年内换过三种后缀，
   `version_guard_test.go` 里不得不写"接受这四种形态"的宽松正则。
3. **和上游版本号纠缠**。上游发 `0.9.72`，我们本地改了东西，版本该叫 `0.9.72` 还是
   `0.9.72-ours1`？每次都要现编，而且和上游对不齐时无法判断"这版是我们改的还是上游的"。

## 决策

**一律用 `YYYY.MM.DD[.N]`**，N 是当日序号（从 1 起，同日多版才出现）。

- `2026.10.23.1` = 2026-10-23 的第 1 个版本
- `2026.10.23.8` = 同一天的第 8 个版本

## 被否掉的选项

| 选项 | 为什么否掉 |
|---|---|
| 继续语义化版本 | 跨树无法比较；与上游纠缠；语义化的 major/minor/patch 语义在本场景无意义（插件对外只有 ABI 版本一个真契约） |
| `YYYYMMDD-N` | 可读性差，且与既有 tag 命名（带点）不一致 |
| 保留代次后缀 `-v8.0` | 正是要消灭的东西。代次信息应体现在 ABI 版本号或 CHANGELOG，不该进版本串 |

## 后果

- **好的**：跨树一眼可比；与上游彻底解耦；正则从"接受四种形态"简化成 `^\d{4}\.\d{2}\.\d{2}(\.\d+)?$`；
  每天有多次发版时序号自然表达"今天的第几版"。
- **代价**：失去了"这版是破坏性变更"的显式信号。**补偿**：破坏性变更必须在 CHANGELOG
  条目标题里写明，并且 ABI 版本号本身会变（宿主会拒绝加载）。
- **什么时候该重新考虑**：如果将来要把这些插件发到公开 registry 供他人依赖，
  那时需要一个能表达兼容性的版本方案，再写一条新 ADR 取代本条。
