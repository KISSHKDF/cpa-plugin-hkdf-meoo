# ADR 机制说明

## 为什么有这个目录

2026-10-23 审计发现：10 棵树的 `docs/adr/` 全是**空目录**。空目录在 git 里根本不存在
（git 只跟踪文件），所以这个"架构决策记录"机制实际上**形同虚设**——
目录骨架建了，但没有任何一条真实决策被记录过。

## ADR 是什么

ADR（Architecture Decision Record）= 一条架构决策的短记录，回答三个问题：

1. **当时要解决什么问题**（背景）
2. **选了哪个方案、放弃了哪些**（决策 + 被否掉的选项及原因）
3. **代价是什么、什么情况下该重新考虑**（后果）

它不是设计文档（设计文档描述"现在是怎么做的"），而是**决策日志**——
记的是"为什么这么做"和"当时排除了什么"。半年后有人问"这个古怪设计谁想出来的、
能不能改"，答案在这里。

## 什么时候写

**触发条件**（满足任一就写）：
- 引入/更换一个外部依赖
- 改变数据持久化格式或存储位置
- 改变对外契约（ABI、HTTP 路由、面板 JSON 结构）
- 采用一个非显然的实现路径（比如"用提示词信封实现工具调用"）
- 决定**不**做某件事（"为什么我们不用 X"），这种最容易被忘

**不写**：普通 bug 修复、样式调整、纯重构——那些走 CHANGELOG。

## 文件命名

```
ADR-0001-<短横线小写主题>.md
```

编号从 0001 起，**只增不改**。决策被推翻时不要改旧文件，写一条新的并在旧文件顶部加
`Superseded by: ADR-XXXX`。

## 模板

```markdown
# ADR-0001 <一句话标题>

- 状态：提议中 / 已采纳 / 已取代（by ADR-XXXX）/ 已废弃
- 日期：YYYY-MM-DD
- 相关版本：<VERSION>（这条决策从哪一版开始生效）

## 背景

当时遇到的具体问题。**要带可验证的事实**（实测数据、日志、上游行为），不要写"感觉"。

## 决策

选了哪个方案，一句话说清。

## 被否掉的选项

| 选项 | 为什么否掉 |
|---|---|
| A | ... |
| B | ... |

## 后果

- 好的：...
- 代价：...
- 什么时候该重新考虑：...

## 证据

指向实测记录、CHANGELOG 条目、或代码位置的路径。
```
